# Simplifying v3 observation indexing while retaining direct Parquet retrieval

27 October 2026. Focused follow-up to Ops [PR #139](https://github.com/TEST-uk-aq/uk-aq-ops/pull/139), under the user's revised requirements. Architectural analysis only; no implementation, conversion, deletion or deployment authority.

## 1. Preferred decision

**Choose Option B: one exact-leaf physical index, directly reconciled with existing canonical manifests and verified Parquet; retire the duplicate `_aligned` representation after compatibility and real TEST acceptance.** Keep canonical v3 observations, manifest hierarchy, binding/continuity, required operational summaries and recovery evidence. Do not add a canonical witness, source catalogue, event ledger or service. Preserve the current index until its replacement verification and every affected consumer are accepted.

The existing exact reader already obtains the physical routing it needs without fetching `_aligned`. The missing work is replacing the writer/verifier/inspector dependency on `_aligned` with direct reconciliation against canonical files and manifests, rather than dropping checks. This delivers a substantial evidence-backed simplification with the smallest format/reader change. Retain independently addressable exact leaves initially; compact JSON is a bounded encoding improvement, not a prerequisite or a second migration project.

**Runner-up: Option C, a compact directory and bounded range-addressable exact records.** It can reduce tiny-object growth and repeated envelopes further, but requires new range adapters, cursor/authentication semantics, staging and pack lifecycle. Current evidence does not show that this extra complexity is needed or that it meets cold Worker CPU headroom. Reconsider it only if actual exact-only TEST size/object-generation/verification measurements show a material problem. Do not build a new hierarchy merely because packing is possible.

This recommendation changes the earlier [complete-system decision](uk-aq-history-architecture-decision-2026-10-27.md) **under new explicit user requirements**: an authorised website Parquet retrieval path is now a permanent requirement, and new witness/catalogue infrastructure is excluded. Earlier retirement-oriented conclusions and PR #5 proposals were conditional on different premises; their recorded measurements remain valid. No historical finding is rewritten here.

**Contract conflict:** the current managed JSONgen contract prohibits automatic Parquet fallback for missing/corrupt managed JSON. The user now requires the website to retain Parquet retrieval and AQI calculation when suitable JSONgen data is unavailable. This report assumes an explicitly authorised physical route for index design; it neither authorises automatic fallback under today's contract nor designs its routing/error/cache rules. A separate accepted chart-routing amendment is required before activating that behavior. Ordinary managed JSONgen still consumes verified handovers and monthly JSON, not routine Parquet reads. Its control/publication/retention architecture is outside this investigation.

## 3. Start with observation_content_hash

### 3.1 Exact implementation semantics

[`uk_aq_observation_content_hash.mjs`](../../workers/shared/uk_aq_observation_content_hash.mjs) defines two different SHA-256 contracts:

| Property | Status-inclusive v1 | Measurement-only v2 |
| --- | --- | --- |
| Fields, in encoded tuple order | `connector_id`, `station_id`, `timeseries_id`, `pollutant_code`, `observed_at_utc`, `value`, `verification_status` | Same first six fields, excluding status |
| Domain prefix | `uk-aq-observation-content-hash:v1\n` | `uk-aq-observation-measurement-content-hash:v2\n` |
| Row encoding | JSON tuple; value encoded as 8-byte big-endian IEEE-754 hex; exact UTC millisecond timestamp; canonical lower-case pollutant; station may be null; status P/R/null | Corresponding six-field tuple; no status/count authority |
| Canonicalization | Validate IDs/fields, normalize negative zero to zero; sort encoded row strings lexically; hash each with trailing newline after the prefix | Same method over measurement tuples |
| Order and multiplicity | Input ordering does not matter; identical duplicate rows are included repeatedly, so multiplicity matters | Same |
| Changes | Value, timestamp, identity, multiplicity or persisted P/R/null change the logical digest, barring cryptographic collision and the explicit normalization equivalences | Measurement changes do; status-only changes do not |
| Additional returned metadata | Algorithm, contract version, columns, hash row count, P/R/null counts and normalized rows | Algorithm, version, six columns, row count and normalized measurements; validator forbids status counts |

`computeObservationContentHash()` and `computeObservationMeasurementContentHash()` reject empty arrays; dedicated empty helpers hash only the relevant prefix. An empty digest is not authority to publish an empty exact-v3 scope. Existing writer-owned removal/complete-replacement rules govern absence.

The hash function itself accepts an array: it does not intrinsically impose one timeseries or UTC day. **Its canonical v3 writer use is a complete UTC day/connector/pollutant partition (DCP), potentially containing many physical timeseries.** `canonicalPhysicalRows()` validates that partition and computes its hash. There is no implied per-series logical value hash just because a series ID contributes to the DCP digest. Sorting for hashing is distinct from physical timeseries/time ordering.

Current seven-column/schema-3 writing uses v1. Measurement-only v2 helpers exist for the separately contracted future verification overlay/schema-4 transition. Function availability is not deployment acceptance. Never compare v1 and v2 digest strings as equivalent; `compareObservationContentHashMetadata()` rejects different versions. Cross-version measurement comparison requires decoding the six common fields and explicitly computing v2. After accepted connector overlay cutover, effective status comes from that authority even for retained schema-3 files; an old embedded-status hash does not authenticate current overlay P/R.

### 3.3 Six identities that must remain distinct

| Information | Already available / what it does not provide |
| --- | --- |
| Logical observation hash | Detects changed normalized DCP rows, independent of physical packing/order. Does not reveal changed series, values, row-group ordinals, byte offsets or change chronology. |
| Canonical manifest identity | Commits the described file set, counts and content metadata through accepted hierarchy. Does not independently prove stored file contents match that description. |
| Parquet SHA-256/byte size | Pins exact stored bytes, including compression/layout. Repacking changes these even if logical hash stays equal. ETag is separately a current conditional-read/race token, not automatically a SHA. |
| Physical membership | Canonical DCP and per-file `timeseries_row_counts` identify members/counts; absent IDs in complete authenticated sets can establish absence. Counts do not identify row locations or detect value-only changes. |
| Physical routing | Single-series groups, ordered segment bounds and time/value column chunk ranges. These are not derivable from a digest; actual footer/layout inspection is needed. |
| Effective verification status | Current accepted embedded/overlay authority, binding to values and source/provenance semantics. Neither a concentration-only response's null status nor measurement v2 authenticates current P/R. |

**What the existing hash permits:** retain one canonical logical content commitment per DCP instead of inventing another logical identity catalogue for this index change; compare authenticated complete logical identities without repeatedly decoding unchanged files in every consumer. Existing verified canonical file identity can be reused under its prescribed lifetime/race rules. It does not permit skipping the original source/output verification, SHA/size gate, physical index validation or needed independent recovery checks. It cannot remove all physical indexing or prove JSONgen complete writer delivery/currentness. Those are separate responsibilities.

Classify checks by responsibility:

- **Canonical integrity:** accepted source rows, serialized values/status, logical hash, complete files/identities, canonical hierarchy, original gate/deletion and independent historical evidence. These survive unchanged.
- **Lookup correctness:** exact member coverage, segment identity/order/caps, actual file/footer-derived ranges, schema/profile, file SHA/size/ETag and conditional ranges. These survive in one index.
- **Duplicate-representation consistency:** exact leaf equals aligned member, aligned source equals canonical source and aligned files/counts agree with canonical. Replace these with **direct** exact→canonical/actual-file checks. Comparing two products of the same builder is not an independent historical-source check worth preserving as a second physical tree.

Canonical hash + manifests + verified files can provide the source-integrity and membership side without duplicated index descriptions. They cannot supply low-cost physical locations. The one remaining physical index still must be independently validated against actual canonical file layout; a logical hash does not authenticate an arbitrary offset.

## 5. Minimum safe physical lookup and chart cost

Retain: deterministic UTC DCP lookup; exact physical series membership/absence; supported per-scope schema/writer/layout/profile; authenticated selected record; file key/SHA/size; chronological row-group/segment identity and counts/bounds; independently decodable observed-time/value chunk offsets/lengths (including required dictionary/page locations); bounded continuation pinned to selected identity. Status/provenance follows its separate accepted authority. No normal runtime footer search or unrelated-series decoding is introduced.

Canonical manifests cheaply provide DCP membership, per-file series counts, file SHA/size and broad bounds **once their objects are read/authenticated**. They do not provide the per-series group and column ranges. Without those, a reader must GET footer ranges and inspect group metadata, or download/decode candidate files; even per-file member counts do not locate a series' groups. A whole-file scan is not a credible replacement for a Free Worker route requiring reliable CPU headroom below 10 ms. Less frequent fallback does not relax an individual invocation's limit.

Preserve exact reader's ≤24-hour low-level request, one ≤1,024-row physical segment per page, explicit no-store/incomplete reasons, bounded range bytes/concurrency and untrusted/stale cursor rejection. Station History splits valid continuity intervals at UTC midnight, shares ≤16-page/5,000-row invocation budgets and uses previous-23-hour PM context. Date-valid cross-network continuity remains above physical reading; no row relabelling or inferred network equivalence. Older observation chunks remain bounded to seven days; browser normal chunk preferences are 6h/1d/3d/7d for 24h/7d/31d/90d views. Longer ranges require bounded orchestration, not relaxed endpoint limits.

| Visible workload | Source-derived cold baseline, one series/segment per aligned UTC day | Implication |
| --- | --- | --- |
| 24 hours | 1 scoped GET + 1 leaf GET + 1 file HEAD + 2 column GETs = 5 Class B operations | Adjacent columns can coalesce: 4 total. Midnight/context/continuity can add scopes. |
| Seven days | ~28 GET + 7 HEAD = 35 | Excludes PM context/status/binding, retries, caches and overlap. |
| 31 days | ~124 GET + 31 HEAD = 155 | Multiple supported chunks; not one unbounded Worker call. |
| 90 days | ~360 GET + 90 HEAD = 450 | Dense pages may hit assembly budgets sooner; progressive results remain bounded. |
| Occasional longer periods | Approximately proportional to days/pages under same assumptions | No assumed annual single-request capability or fallback traffic rate. |

Option B preserves this chain: removing `_aligned` supplies **no intrinsic chart GET reduction**, because it is already skipped. It should remove writer/verifier work, not be advertised as measured chart acceleration. Warm complete-response cache hits bypass physical work; cache identities must include compatible selected format/schema/status mode and correction behavior. No hit rate is known. A/C old/new-format failures remain explicit; no whole-Parquet/cross-generation/error-triggered format retry is introduced.

Current directory/leaf parsing, SHA checks, ZSTD decoding and Station History merge/AQI still consume CPU; HTTP waiting is wall time. Sparse scopes may be directory-dominated, high-cardinality scopes enlarge the directory, and high-frequency series enlarge segment lists/pages. Removing `_aligned` solves duplication, not unlimited scale. Record cold CPU/tails, heap where available, bytes and first/full chart settlement through real TEST operations after separate deployment. An occasional cold fallback is precisely where warm-cache assumptions are weakest.

### 6.1 Why not put the index in canonical manifests?

An existing per-file member table is useful for choosing candidate files, but adding all row groups and column ranges to it essentially embeds the physical index in canonical metadata. This enlarges every authenticated DCP read, couples encoding/reader changes to canonical manifest hashes and backup/recovery, and requires changing canonical ownership. A monolithic manifest also transfers unrelated-series locations for one request. Adding a pointer to bounded separate records recreates an index. Retain canonical manifests as source authority and keep the physical routing derived and independently rebuildable.

C deserves later measurement if L/object verification becomes the dominant cost. Start conceptually with one directory and independently hash/length-pinned exact records; shared file descriptors can save space but must remain available to continuation without hidden extra reads. Use bounded packs only when occupancy/operating evidence justifies them, never whole-gzip random seeking or unbounded whole-shard parsing. This is why C is a runner-up, rather than the first implementation.

## 7. Exact-only integrity and dependency closure

The canonical writer can validate actual Parquet schema, single-series groups, segment coverage/counts/time bounds and footer-derived ranges once, reconcile every exact member/file against canonical output, then publish **one** physical index. Keep file readback, durable evidence, bottom-up prerequisites, exclusion and canonical finalisation. Replacing cross-checks between generated copies with direct checks against actual files preserves their useful guarantee without persisting a second physical representation. Do not claim file SHA alone verifies the logical-to-physical mapping.

Value-only corrections change v1/v2 logical identity and ordinarily physical file SHA even with unchanged counts. Regenerate affected routing from current output, not old leaves. Repacking can preserve logical hash but changes file SHA/size/offsets, so routing must change. V1 status changes affect logical/file identity; accepted future overlay status changes instead require the separate effective-status authority/cache invalidation while unchanged measurement offsets can remain. Complete removal uses authenticated final membership/parent removal and explicit writer ownership; referenced 404 is failure, not absence. Old loose leaf existence never restores removed membership. No zero-row exact manifest is invented.

## 8. Consequences for proposed Contract A, not Contract B

PR #5's A §1/§4 assumes routing can disappear and proposes DCP certificates plus a canonical witness. The new user requirement establishes the physical reader's legitimate long-term need. **Do not adopt that proposed architecture merely to remove duplicate aligned objects.** A SHA-committed canonical manifest plus verified exact index is sufficient for source membership and physical retrieval under existing writer/read integrity boundaries; it is not a claim of complete JSONgen all-writer freshness.
