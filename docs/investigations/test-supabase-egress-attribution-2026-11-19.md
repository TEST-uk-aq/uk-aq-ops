# TEST Supabase egress attribution investigation

19 November 2026 · All dates and times are UTC · Evidence window 1–19 November 2026

## A. Executive summary

TEST IngestDB's 10 November comparison combines a project-wide provider meter with selected client-side measurements. The approximately **89.04 MB PostgREST** and **15.87 MB Shared Pooler** differences are useful leads. The evidence does not establish an amount of missing payload for either category.

- **Confirmed parallel PostgreSQL traffic on 10 November.** Five Prune Daily runs started, including three failures. Three runs produced **24,207,123 combined socket bytes** over source streaming and deletion revalidation, independently reproducing the supplied 24.21 MB. Daily Stations also validated an IngestDB Shared Pooler DSN and completed. The nightly backup executed large database reads against both TEST projects. The backup's own logs measure the resulting files and mask its DSNs. This leaves the backup's direct-versus-shared transport and provider byte attribution open. **Counting failure modes.** HTTP bodies can go missing when the request fails before a readable response, a wrapper measures after parsing, or declared length is absent. Header-based length is encoded, while HTTPX, Python Requests and the explicit text-based collectors normally see decoded content. Decoded length can exceed transmitted content length. Comparing adjacent windows can shift a long operation because collectors timestamp completion. Paginated and retried network calls are distinct even when they return the same rows. Duplicate persistence is different: the ObsAQIDB RPC is additive, so an uncertain-success batch replay can overstate counters. Shared Deno/Python collectors can retain failed batches and clear a snapshot after success, which creates loss or replay risk where a warm runtime records or flushes concurrently. Local dashboard and Phase B clear before the send and can lose the batch on failure. Future measurement at a wider boundary should replace or exclude existing observations for the same hop. Counting the provider's REST response, the downstream Edge/Worker response and the collector's own telemetry reply as one `supabase_postgrest` event would mix boundaries. ### How the difference can arise

1. **Missing clients and operations.** Every independent HTTP client in §C can produce traffic included in a project-wide PostgREST total. The best bulk-body candidates are Daily Stations/Core mirror, station and timeseries reference/observation reads, and Prune repair results. Daily Stations logs and its unmetered `GET /rest/v1/timeseries` and `GET /rest/v1/stations` call sites confirm a substantial row-reading workload on 10 November. Later Gateway evidence confirms other recurring endpoint families. There is no 10 November response-size distribution by caller. Start with high-returning pages before adding counters to every small operational request. [10 November Daily Stations job](https://github.com/TEST-uk-aq/uk-aq-ingest/actions/runs/42746517452/job/129599832336)
2. **Accounting scope.** Client counters omit response headers and transfer framing, unless represented by the separate PostgreSQL stream measurement. Even a 204 or empty write response carries protocol overhead. With thousands of requests it can add up if the provider includes it at the metering layer. Supabase's public guide does not specify whether the REST meter includes headers, gateway framing, TLS or transport retransmissions. The encoded body and decoded body can differ in either dataset relative to the provider meter, depending on the metering layer. A decoded metric reversing part of a network-overhead difference is possible. Adding fixed bytes per request or applying a compression factor without paired evidence would mislead. [Supabase egress accounting](https://supabase.com/docs/guides/platform/manage-your-usage/egress)
3. **Unmeasured and misclassified responses within known clients.** Missing `Content-Length` on the Deno shared ObsAQIDB direct adapter becomes zero even when a response exists. Network and malformed-body failures, capped Worker reads and failed flushes can remove bytes. The length-only defect is on the ObsAQIDB direct delivery path and should not be used to explain IngestDB's gap without a matching IngestDB call site. Confirm effective collector enablement, exact environment and coverage before estimating losses by producer. [Length-only adapter](https://github.com/TEST-uk-aq/uk-aq-ingest/blob/98dace36f812f50485f32ef7fbfae479fa87e4bf/supabase/functions/_shared/service_egress_metrics.ts#L364-L409) · [Capped HTTP read](https://github.com/TEST-uk-aq/uk-aq-ops/blob/fae93e96855df5e4878abf2368a11fc4098a36c1/workers/uk_aq_dashboard_online_api_worker/src/lib/direct.ts#L390-L424)
4. **Provider traffic outside monitored apps.** Project Studio, SQL/API explorers, other clients, integrations and provider services can contribute. No retained evidence quantifies them for 10 November. Check the provider's service split before folding in Auth, Functions, cached usage or log drains. Use raw bytes, identical window boundaries and matching project/branch selection before comparing totals. [Supabase Usage page and custom reports](https://supabase.com/docs/guides/platform/manage-your-usage/egress#view-usage)

### Supabase billing definitions used in this report

| Provider boundary | Comparison to UK AQ |
| --- | --- |
| **PostgREST / Database Egress** | Supabase calls REST API traffic Database Egress in its guide, corresponding to the supplied PostgREST service label. Server-side and browser table/RPC HTTP requests both use the PostgREST API. Calling an SQL function via `/rest/v1/rpc/...` uses that boundary. Calling the same function through a SQL driver uses the chosen PostgreSQL connection. An Edge Function may make a separate nested REST call, and its reply to its own caller is a distinct Functions hop. Historical same-platform/internal treatment and service labels still need provider evidence. |
| **Shared Pooler** | Supavisor customer-facing egress for session or transaction connections. The guide explicitly excludes the database-to-Supavisor leg from separate Database Egress to avoid duplicate billing. Provider scope is wider than two Phase B client intervals. |
| **Direct PostgreSQL / dedicated pooler** | Supabase documents the direct `db.<project-ref>.supabase.co` connection and distinguishes shared session (5432), shared transaction (6543), and dedicated pooler. Direct network data retrieval is within the guide's general database egress description. The cited public billing guide does not give a separate dashboard label or exact counter for every native mode. Confirm its treatment with the project usage export or Supabase. UK AQ's `supabase_postgres` identity by itself does not resolve this. |
| **Cached and other egress** | Supabase cache hits generally come from its CDN, typically Smart CDN for Storage, with distinct quotas/rates. A Cloudflare/R2 or MySQL cache hit is an application behaviour and may avoid a Supabase request entirely. Auth, Storage, Realtime, Functions and outbound log drains follow their own boundaries. An organization-wide total can include project aggregates and cached egress. Log ingestion and Gateway log serialization are separate. |

Supabase specifies externally transferred network data as the basis for egress. Its public guide does not document the byte-level treatment of HTTP headers, encoded payloads, TLS framing, retransmission, or native accounting for every connection mode. The UK AQ body/stream estimates remain valid for application attribution within their measured scope.
