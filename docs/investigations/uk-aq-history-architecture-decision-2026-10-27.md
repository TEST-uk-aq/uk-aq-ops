# UK AQ historical architecture: final v2/v3 and JSONgen decision

27 October 2026. Documentation-only extension of [PR #139](https://github.com/TEST-uk-aq/uk-aq-ops/pull/139) and its [storage investigation](r2-v3-index-storage-efficiency-2026-10-27.md). This is a recommendation, not implementation, migration, deployment or deletion authority.

**Later focused decision under revised user requirements:** [Retain efficient Parquet retrieval with one exact-only index](v3-exact-only-index-decision-2026-10-27.md). The user now requires a permanent website physical retrieval capability and excludes a new witness/catalogue. That focused decision supersedes this document's conditional physical-index retirement/catalogue recommendation for the new scope; measurements and historical reasoning below remain unchanged. JSONgen control/publication design is outside the follow-up scope.

## 1. Decision

**Keep canonical v3. Complete the bounded AURN JSONgen experiment and the managed publisher's integrity boundaries. Do not begin an index rewrite or return to v2.** V3 delivered a useful bounded physical-access design; it did not establish universal storage, request-count, writer-cost or latency superiority. Accepted JSONgen serving would remove much of the historical chart workload that justified that design. It would not make the retained v2 generation current, remove canonical recovery requirements, or release any index objects under current contracts.

**The preferred long-term architecture is canonical v3 plus tiered serving, paired monthly observation/AQI products and the smallest authenticated membership/change metadata needed by real consumers.** Reuse the canonical manifest hierarchy, verified writer completion evidence, binding and effective-status authority. Prefer a compact, reconstructable catalogue of those dependencies over permanent daily Parquet byte routing if the remaining consumers need only metadata or bounded batch access. A catalogue is a derived certificate of canonical state, never a competing observation authority. Its complete proof protocol remains a condition, not an established achievement.

Retain **one** compact physical lookup representation only if a supported frequent low-latency consumer remains after chart, WHO provenance and administrative decisions. If metadata equivalence cannot be demonstrated, keep the necessary present metadata until it can. The choice between full routing retirement and that residual lookup can wait for real TEST acceptance. The physical v3 Parquet layout and the present exact/`_aligned` encoding can evolve independently.

**Returning canonical/index_v2 is not advisable on current evidence.** Its credible attractions are simpler coarse metadata and potentially better whole-partition compression/batch decoding. Neither advantage has a matched measurement. The latter batch access is already possible against v3 without the online index. A reversal requires a new complete, verified generation incorporating every post-cut-over addition, correction, removal, status and identity change; changing `UK_AQ_R2_HISTORY_VERSION` alone would select stale history. It would retain canonical-plus-JSON/evidence duplication and substitute another index/currentness reader.

Do not change Ops PR #136 or website PR #79 for this investigation. No structural defect established here requires delaying their bounded, separately authorised P2 operation. Managed implementation does need complete all-writer currentness/fencing and bounded atomic control-state design before selection is enabled. Those are genuine managed-publisher gates; they are not a new prerequisite for the isolated experiment.

## 3. Why v3 existed, and what it delivered

The original problem was unsuitable request-time work for one series: coarse file-range discovery, downloading candidate files, inspecting footers and decoding unrelated-series identifiers/rows. Large/high-frequency networks made that work and Worker bounds particularly important. V3 added exact authenticated membership, single-series physical segments, offline-established column ranges and explicit physical paging. It was not a migration from uncompressed storage to compressed Parquet: **both generations already use Parquet and ZSTD**. [R3–R4]

| Dimension | Canonical/index_v2 | Selected canonical/index_v3 | Evidence-based conclusion |
| --- | --- | --- | --- |
| Canonical organization | Day/connector/pollutant files and manifests under v2; serializer defaults to 50,000-row groups, not a measured size for every retained file. | Separate complete generation; same logical observations; deterministic timeseries/time ordering and packed files. | Generation separation and semantics are explicit. A generation number alone adds no observation correctness. |
| Packing/compression | Larger groups can amortise page/footer overhead and suit full-partition scans. | One physical timeseries per independently decodable row group, at most 1,024 rows; target 65,536/max 131,072 file rows, target 4/max 8 MiB, max 128 groups/file. | Bounded exact decoding is established in code. Smaller groups can cost compression/metadata; no matched canonical-byte advantage is demonstrated. |
| Discovery and physical reads | File min/max-ID ranges do not prove exact membership. Legacy reader gets full candidate Parquet before footer/series-column work. | Scoped manifest → SHA/size-pinned exact leaf → Parquet identity HEAD → conditional time/value range GETs; no runtime footer or series-column decode. | Less irrelevant transfer/decode is structurally achieved. More dependency operations can offset it for small sparse files. |
| High-frequency safety | Candidate file/group size governs work; unrelated data may be scanned. | One segment/≤1,024 physical rows per low-level page, bounded bytes/concurrency and explicit continuation. | Stronger work bounds; a dense series may need many pages. Station History's ≤16-page/5,000-row budget still limits a result. |
| Index size | Coarse daily file-range metadata and latest. Same-population bytes/counts unknown. | Exact leaves and `_aligned` duplicate segments plus parent descriptors, verbose uncompressed JSON. | Precision delivered at substantial metadata cost. Supplied full index 4.420 GiB exceeds complete `history/v3` 3.718 GiB; this is not a matched observation-only ratio. |
| Historical query speed | Fewer metadata steps possible, larger full-file transfer/CPU. | Smaller exact column transfer, more bounded invocations/daily discovery. | No controlled current v2/v3 cold/warm latency or CPU comparison. Do not call every v3 request faster or cheaper. |
| Writers/finalisation | Canonical/hash/index/Prune gate consistency still necessary. | Footer/range validation, two metadata representations, dependency-ordered verified publication and latest finalisation. | Better explicit physical proof, more objects and verification work; not a simplicity win in every dimension. |
| Integrity/recovery | Fixed-v2 capabilities exist, but old data are not automatically current. | Canonical-backup-guided deterministic reconstruction; scoped real TEST repair evidence with documented limits. | Shared proof/rebuild capability is useful; code and a scoped acceptance do not establish every network/writer is accepted. |
| Backup | Canonical files/manifests, Core, bindings, run/inventory evidence. | Same canonical principle; bulk exact/`_aligned` trees excluded, compact latest retained. | V2 return does not remove a full-index backup burden: that burden is already excluded. |

Historical calibration of 25–26 files becoming 10 concerned the superseded 8,192/16,384-row `timeseries-bounded-v1` design. It is **not** evidence of savings for the selected 1,024-row `timeseries-aligned-v2` layout. Likewise the 12 October CPU cohorts (station-series median 15 ms versus observation-history 4 ms; AQI-on/off 17/5 ms) are not a controlled v2/v3 benchmark. [R1, R3]

One concrete later operating cost is the reported 24 October TEST Prune: **5,453 canonical dependency GETs and 310,230 ms exact latest/global verification**, with eight concurrent reads. That is dated workload evidence, not a rate for every writer. Its zero reuse/recovery counters do not accept those unexercised cases. V3's bounded access and physical identity protection are useful delivered properties; universal lower storage, lower CPU, fewer requests, faster writers and simpler operations remain unproven. [R1, R5]

### 3.1 The strongest case for returning to v2

A predominantly offline baseline job could prefer fewer/larger groups and coarse file membership. V2 might have a smaller canonical footprint or cheaper full-file decode. The proper comparison is **matched current logical data**, including status/multiplicity and all index/recovery costs, rather than old retained v2 bytes versus a newer v3 population.

However, v3 files can also be read once per partition by an offline batch job. JSONgen's current Dropbox bootstrap already follows canonical manifests and decodes files without the online exact tree. Ordinary managed increments are intended to use verified writer replacement bundles plus authenticated existing monthly JSON/context, not to decode canonical Parquet of either generation. Returning to v2 therefore would not simplify the normal incremental input path. It might affect initial bootstrap or exceptional reconstruction, for which no matched timing/CPU/memory evidence favors v2. [R4–R6]

Technically attractive in a narrow hypothetical batch/compression comparison: **possibly**. Operationally viable as a complete separately authorised reverse migration: **yes in principle, with substantial work**. Justified now or once JSONgen runs: **no evidence of an overall advantage**. A demonstrated large canonical-format benefit could reopen that decision later, after comparison with simply batching v3 or changing its physical packing under a new contract.

The distinction between canonical science/batch consumers and metadata-only consumers is decisive. Their continued existence does not automatically justify fast daily Parquet access. Conversely, moving charts does not remove today's writer, verification, provenance or API dependencies.

**A** is the practical immediate coexistence state, not an efficient permanent default. Its minimal migration risk is real; its duplicate trees, JSON products, receipts and global verification cost are also real.

**C and D** separate physical storage from proof representation. C authenticates existing canonical manifests and retained complete writer evidence through bounded batch interfaces, without a new permanent source catalogue. D adds compact durable currentness/membership certificates when they reduce those repeated scans. Prefer C if its bounded operations are sufficient; otherwise D is the preferred implementation direction. Reuse existing authenticated descriptors instead of inventing another full index. Neither permits dropping scope/value/status/supersession checks, and neither is already implemented as a complete replacement.

**E** is justified only by a demonstrated remaining interactive consumer. The original report's range-addressable records can preserve selected-record access while hoisting shared metadata and removing `_aligned`. Whole compressed 1,000-ID shards would decode unrelated records, so they are a weaker default. Per-object gzip/minification alone leaves object and verification growth largely intact; it should not precede another rewrite without evidence.

**F1** deserves consideration because immutable events already exist and replay can avoid copying their entire contents into each control revision. It is a possible bounded implementation of D, not a new source of canonical ordering. A log of known events cannot prove no unregistered writer/change occurred. Complete writer coverage, checkpoint membership and current-root reconciliation remain necessary. Do not introduce a numeric global cross-writer sequence as a substitute for canonical supersession.

**F2** can provide transactional metadata lookup, but a database transaction cannot atomically commit canonical R2 and JSON products. Existing DB capabilities avoid installing a service, not schema/capacity/egress/restore coupling. D1's limits/serial-per-database model require capacity design; the original report records 500 MB Free/10 GB Paid limits. Those figures are previously checked product documentation, not a fresh account inspection. KV's eventual consistency, including negative reads, is unsuitable as mutable membership/publication authority. Immutable SHA-keyed caching is a separate possible optimisation without a measured need. No new service is justified for today's byte savings. [R1]

**F3** could improve full-partition compression and object counts. Monthly canonical objects amplify single-day correction/removal writes, Prune gates, locking and backup units; larger/multi-series row groups change accepted decode guarantees. No measured physical-format defect requires that migration now. Canonical v3 can first be batched without repacking.

The already contracted future verification overlay is a narrower promising alternative for **status-only correction amplification**: accepted connector overlay authority can avoid rewriting measurement Parquet/indexes solely to change P/R, including while older physical schemas remain. It still requires authenticated effective status and invalidation of status-dependent products. It is not current operational acceptance or a reason to bundle a schema/overlay migration into P2. [R12]

**F4** deserves separate consideration if real TEST shows repeated AQI calculation dominates while storing monthly observation copies is costly. It keeps physical observation discovery/reads and requires an authenticated source-snapshot protocol so a corrected canonical response cannot be combined with stale AQI. An AQI digest alone does not supply that coherence; retaining immutable observation snapshots or repeated source authentication could erase its savings. It conflicts with the current matching-pair publication contract and is unproven, so do not adopt it before P2.

**G is a serious counterfactual.** Precomputation adds full-month rewrites, retained evidence and another publication system. If real TEST shows low historical demand, insufficient serving CPU benefit, excessive correction amplification or unsustainable managed operating cost, retaining the current normal route while revisiting JSONgen is preferable to forcing an unproven cutover. Existing CPU/budget pressure and repeated historical AQI work make JSONgen worth the bounded experiment; they do not prove it wins total cost. Reject on-demand generation of missing managed months as an escape hatch: that would add cold request-time decoding/calculation and violate the no-automatic-Parquet-fallback boundary.

The strongest additional whole-system alternative is therefore **tiered serving combined with D**, rather than a different canonical generation or new database: stable selected monthly products, a separately specified recent/open-month seam, metadata-only currentness, and manifest-guided administrative/scientific/recovery batches. The unresolved Prune-to-JSON publication gap must be solved before that tier can retire physical chart access. It is distinct from forbidden fallback after corrupt managed JSON.

## 6. Total storage, object growth and costs

### 6.1 Accounting boundary

Sum canonical and derived buckets/accounts, local/remote recovery copies where applicable, active and retained generations. Define:

```text
Net storage change = additional derived storage + replacement metadata - retired storage
```

`additional derived storage` includes compressed monthly observations, precomputed AQI, original pending/source bundles, authenticated selected bundles/receipts, immutable original metadata evidence, publication manifests/evidence/selectors, control/checkpoints/events, superseded monthly versions, intermediates and abandoned candidates. Mandatory originals cannot be counted as removable duplicates merely because their information also exists in canonical history. `replacement metadata` includes required membership/status/binding/currentness and reconstruction references; never set it to zero by omitting a proof. Common canonical backup costs do not vanish with a chart switch. JSONgen remains outside canonical Dropbox history backup. [R1, R5, R9]

At the report's previously checked illustrative Standard R2 marginal rate $0.015/decimal GB-month, 1.523 GiB is about **$0.0245/month**, 4.407 GiB about **$0.0710/month** before replacement/JSON bytes, allowances and billing rounding. The 2.68–3.25 GiB sensitivity saves about **$0.043–$0.052/month gross**. These small amounts are not account invoice savings. Original illustrative operation rates are $4.50/million Class A and $0.36/million Class B; one million PUTs costs much more than the present marginal storage saving. Cache/Worker/DB charges, actual storage class, allowances and traffic remain unknown. Avoid an index project justified by pennies alone. [R1 §6.4]

### 6.3 Growth and measured amplification

For `Q` populated day/connector/pollutant scopes, `L` series/day memberships and `A` occupied aligned ranges, present observation metadata is approximately `L+A+2Q+1` objects including latest. Dense-series growth adds segment bytes; more physical series/days adds envelopes even for one row. E replaces leaves with occupied packs `Packs`, approximately `Packs+Q+1`; record/segment information still grows. D should grow with necessary memberships/dependencies/events, with no obligation to retain Parquet byte offsets. Per-component supplied object counts are unavailable.

For `M` physical-series/pollutant/month publications and retained versions `V_m`, the pair alone is `2×sum(V_m)` objects. Managed publication manifest and evidence can bring that publication layer to roughly `4×sum(V_m)` before deduplication, plus source/receipt/event/control/selector objects. No exact total is implied. Daily open-month replacement rewrites monthly products; PM boundary correction can create a new following-month pair even when its raw values do not change.

Dated reported TEST evidence, with its actual limits:

- One seven-day/166-observation candidate: **2,095 observation-gzip + 7,955 AQI-gzip = 10,050 bytes**. AQI was ~3.8 times observations in this one sample; not a month/network compression ratio.
- 433 local candidate pairs: **11.937085 MB including evidence/reports**, not retained R2 monthly products; reported generation 316 seconds/71,704 observations, not an architecture benchmark.
- One 24 October original source: **138,339 compressed bytes**, plus **1,816,634 compressed original metadata-evidence bytes** representing 2,003 objects/18,682,638 uncompressed JSON bytes. Supporting bodies total **1,954,973 bytes** before receipts/control/products.
- Two original AURN events: 12 selected bundles/12 receipts; **866 selected day-scopes/19,878 observations** authenticated. Control grew **761,009 → 1,308,652 bytes**. Seven separate currentness partitions matched selected metadata; that did not establish a coherent current-state fence or all-writer completeness. [R5]

These observations make evidence/control growth a structural concern. They do not support multiplying a seven-day AQI ratio, source gzip ratio or one-event control increment into a guaranteed all-network forecast.

## 7. Currentness and the smallest safe catalogue

### 7.1 What exact and `_aligned` prove today

`scripts/jsongen/authority.mjs:readCanonicalScopes()` does substantially more than the chart range reader. Its canonical root→year→month→day→connector→pollutant walk authenticates current hierarchy and files. The exact scoped manifest authenticates the complete physical member set against canonical `timeseries_row_counts`; the selected SHA/size-pinned leaf supplies row counts, physical schema and ordered file/segment references. Missing membership in authenticated complete authority is different from an unlisted loose object.

The inspector then GET-authenticates the aligned scoped manifest and selected aligned child. It verifies the canonical pollutant descriptor, shard range/membership/counts and referenced file SHA/size against canonical files and the selected exact leaf. It additionally authenticates selected binding/continuity and effective status authority. Ordinary chart range reads validate aligned reference shapes but do not fetch those bodies. Thus `_aligned` is currently duplicate physical metadata **with a real proof dependency**, not safely deletable unused chart residue. Scope digests include more than counts. [R6; R1 §7.3]

This metadata inspection does not independently re-decode source values. It relies on authenticated complete verified writer evidence tied to canonical publication. Equal counts cannot detect value-only corrections; matching one current root/hash cannot prove every writer change was captured, original bytes match final authority, a removal was registered, or seven separately observed partitions formed one coherent snapshot.

### 7.2 Replacement proof obligations

The simplest plausible replacement is a **derived view of existing canonical commitments and verified completion evidence**, with compact immutable per-partition/state pages and one bounded authenticated root. Start from existing manifests/receipts; add only missing information. It must establish all of the following before replacing current checks:

| Guarantee | Required certificate/protocol; insufficient shortcut |
| --- | --- |
| Complete scope membership | Root-selected complete day/connector/pollutant inventory, physical series membership and exact scope bounds. Counts or a list of received events alone do not establish completeness. |
| Relevant values/content identity | Writer-verified logical/source hash and authenticated final file/status identities bound to replacement rows. If per-series hashes are absent, conservatively invalidate every member of a changed shared-file/partition dependency rather than claiming unchanged series. |
| Authoritative absence/removal | Authenticated complete replacement or explicit writer-owned removal linked to previous scope and current canonical absence; never infer deletion from missing receipt/object. |
| Complete verified writer coverage | Inventory of every applicable Prune/Integrity/SOS/backfill/direct-R2/status/binding change path, complete committed scope inventories and unresolved/missing-handover detection. Unknown coverage stays ineligible. |
| Supersession/currentness | Original immutable source-as-of evidence plus authenticated later state/removal dominance, current source-root/status/binding identities and a coherent publication fence. Latest timestamp, registration order and a new global event number are not canonical authority. |
| Status/continuity | Effective P/R/null authority under actual schema/overlay mode, verified physical bindings and date-valid continuity, including status-only changes. A value hash alone cannot substitute. |
| AQI invalidation | Complete affected-month dependency set including prior/following PM context; select newly required matching pairs atomically under the accepted control protocol. |
| Recovery | Immutable original evidence/receipts, code/schema/algorithm identities, canonical/backup reconstruction references, authenticated checkpoints and deterministic replay/reconcile. No automatic canonical reread when managed JSON is missing/corrupt. |

Writer coverage must be anchored to canonical completion under the applicable exclusion/commit protocol. A catalogue and event log both miss a writer that can change canonical state without updating their accepted completeness fence. A before/after root comparison can help detect drift only within a protocol that also proves complete registered coverage and status/binding dependencies; it is not by itself a cross-writer snapshot transaction.

Use conservative broader invalidation where it makes the proof simpler: a shared canonical file hash change can invalidate all dependent months even when one series is unchanged. That can trade extra regeneration for avoiding an unproven per-series equality claim. Broader invalidation does not authenticate replacement rows or permit reuse of an unproven baseline: regenerate only where complete retained final-writer evidence proves all affected scopes. Otherwise retain the prior safe pair, mark freshness unknown/reconcile-required, and require separately authorised reconstruction. Measure amplification later; do not invent finer value authority solely to minimise writes. Canonical batch reconstruction can establish a new baseline/checkpoint only under its explicit authority, not silently repair ordinary missing handovers.

No current code/contract establishes this full replacement. The current exact/`_aligned` inspector must remain until an accepted adapter provides equivalent guarantees. Keeping canonical v3 does not oblige keeping byte ranges inside that future catalogue. Keeping original historical receipt decoders does not oblige retaining the live old index tree forever.

## 8. JSONgen design: retain required products, remove avoidable duplication

### 8.1 Experimental versus managed publication

PR #136 and PR #79 implement a finite configurable AURN **source-as-read experiment**, not a VERIFIED managed monthly publisher. The configured 90-day Bristol operation spans four monthly pairs including the October boundary fragment and hidden context from 2 July; six identities are user-confirmed while complete source/status/currentness admission remains an operator task. Private infrastructure approval and deployment are separately gated. Neither merge is inert: the PR handovers identify deployment workflow effects. No merge/deploy is part of this investigation. [R11]

The experimental publication UUID selects a whole finite sample/revision. **Do not carry that model into managed publication**: managed pubID remains per physical timeseries, pollutant and UTC month. Reuse an unchanged month's selected pair when authenticated observation/status/algorithm/context dependencies permit it. When adjacent PM context requires recalculation, publish/select a new atomic matching observation/AQI pair even if next-month observations are unchanged. Never mix observations from one pubID with AQI from another. [R5]

The pilot downloads/hashes complete referenced Parquet files, then decodes selected exact row groups; it does not use indexed column ranges to reduce source HTTP bytes. Files are reused within each export, while separate sample exports may reread shared files. This exploratory cost warrants real P2 measurement, not a new prerequisite code change. Managed ordinary increments use different inputs: authenticated monthly baselines and complete verified writer bundles. [R11]

### 8.2 Monthly format alternatives

Retain two separately retrievable gzip files for now. They allow observation-only demand to avoid AQI bytes, and preserve independent caching/use while selection authenticates one pair. Combining them can save one object/request for a caller always needing both and share envelope/compression redundancy; it also forces observation-only readers to download/parse AQI, couples transfer/cache reuse into one body and retains two logical dependency sets in that body. It does not add logical invalidation beyond the current atomic matching-pair rule. The small sample's AQI-heavy bytes make over-read a credible cost. It is insufficient to choose an all-system ratio or rewrite the accepted pair contract.

Consider later, only with real demand/size/CPU evidence: a combined observation/AQI product; compact arrays/regular timestamp encoding; independently blocked monthly products for dense networks; columnar/binary monthly serving; observations plus a separate derived AQI cache. Binary/blocking adds decoder/schema compatibility and bounded-decompression/range-authentication work. Computing AQI at request time restores Worker CPU; browser AQI would change established ownership. Any combined/single-product or materially different publication model conflicts with current paired-publication contracts and requires an explicit accepted amendment.

Payloads need their required schema, physical identity, month/time bounds, pubID and interpretation metadata so an object cannot be interpreted under the wrong source/algorithm. Immutable authenticated manifests can carry bulky dependency lists and source/algorithm documents by strong content references if the format contract permits; the payload/manifest relationship must be authenticated and resolvable offline for recovery. Do not remove currently required self-describing fields or duplicate metadata merely because it appears redundant. Start future deduplication with repeated large proof bodies, not tiny safety envelopes.

### 8.3 Original evidence and receipts

Preserve mandatory immutable evidence exactly, including historical index bodies already captured in original proof bundles. Replacing current indexes does not erase those retained copies. For **future events**, a reviewed format could reference shared immutable content-addressed original bodies using exact SHA/size and complete authenticated membership instead of embedding identical large bodies repeatedly. Source availability/retention and independent authentication must remain guaranteed; a mutable or unauthenticated pointer is insufficient. Receipts can reference authenticated immutable source/gate/status records without copying every body into active control, while original receipts themselves remain intact. Do not rewrite originals, weaken authentication or expire recovery-required handovers.

### 8.4 Bounded control and atomicity: a decision needed before scale-up

Current `control.mjs` retains full receipts in `registered_changes`, event references in `authenticated_events`, and repeated desired/applied change IDs and failure state by month. It reads/clones/validates/rewrites the complete control object under a strong-ETag conditional PUT. `MAX_CONTROL_BYTES` is **4 MiB**, explicitly an admission cap rather than accepted scale; selection still throws unconditionally. Reported growth to 1,308,652 bytes after two original events is already ~31% of that byte cap. The bounded currentness accounting admits 1,024 total scopes and 128 inspected per invocation: 866 already registered scopes plus another comparable 433-scope day would exceed that accounting envelope, without implying every future event has that shape. Increasing byte/scope caps alone does not solve transfer, parse/clone, CAS conflict or unbounded event/month growth. [R5–R6]

**Choose the bounded atomic authority model before enabling unbounded managed registration/publication.** Preferred direction: immutable content-addressed receipt/event/state pages, bounded live references/checkpoints, and one small strong-ETag CAS root selecting a complete state generation. Prepare and authenticate all changed pages and affected month-pair selectors before changing that root. Unchanged pages can be reused. The root must bind the complete desired/applied dependency set and all affected months; all readers/reconcilers must obey the same root. This is an architectural protocol proposal requiring contract approval, not a drop-in change to today's control schema.

A hierarchy reduces root/body growth only if child sizes, lookup depth, live work sets and checkpoint/replay are bounded. It adds some metadata GETs. An append-only event journal plus authenticated checkpoints may be simpler for ingestion/replay; compare it against immutable state pages, retaining canonical-state supersession. Do not split month selectors or registration authority into independently mutable objects and claim cross-month atomicity. Partitioning independent control domains is acceptable only after an explicit protocol defines ownership, transactions spanning domains and recovery; it is not assumed here.

Keep old control/evidence formats readable. A crash before CAS leaves unselected candidates; after CAS readers see the complete chosen dependency set. Root-last publication without a reader that actually follows that root supplies no atomicity. Control authority and canonical currentness fencing are separate requirements; solving one does not solve the other.

### 8.5 Dependency-aware retention questions

No garbage collection is implemented or authorised. Define later retention from reachability and recovery needs, not a uniform TTL:

| Object class | Required retention boundary |
| --- | --- |
| Selected pair/manifests/control pages | Active selected roots and all authenticated dependencies remain available. |
| Superseded pairs | Preserve cached-reader/pubID discovery windows, in-flight requests, rollback, reconciliation and audit/recovery dependencies. Browser/CDN retention can outlive selector TTL. |
| Abandoned local/remote candidates | Classify only after proving never selected, not referenced by a crash-recovery journal/CAS outcome and not still being uploaded. Distinguish safe local scratch from authenticated originals. |
| Original source/evidence | Mandatory immutable originals remain exact under their accepted retention rules. Future deduplication cannot delete a shared body still referenced by any retained original. |
| Unresolved handovers/receipts | Keep until canonical completion, authentication, supersession and reconciliation/recovery obligations are resolved; failure to publish is not permission to erase evidence. |
| Event checkpoints/old control generations | Retain complete replay/verification chain and compatible code/schema identity until accepted compaction/reconstruction replaces it without changing original meanings. |

## 9. Retrieval, computation and operational resilience

### 9.1 Request patterns and honest cost models

Current v3's simple cold one-series/one-UTC-day/one-segment model is scoped manifest GET + leaf GET + Parquet HEAD + two column range GETs: **4 GET + 1 HEAD**. Adjacent ranges may coalesce to one; dense pages, continuity/status/context add work. Under those assumptions a seven-day interval is ~35 Class B operations, a 30-day month ~150 and 90 days ~450 before other layers. These are source-derived operations, not invoices or measured latency. Existing browser progressive chunks/cache/concurrency mean they are not browser HTTP counts. [R1 §§5.1–5.4]

The isolated precomputed experiment is also not merely two R2 GETs per month. With its selector/counterpart checks, for `M` intersecting months the dual-product browser path is approximately **`2+2M` HTTP requests and `3+8M` R2 GET/HEAD operations**, excluding auth/proxy/retries: catalogue GET, sample-manifest discovery and per-product manifest/data/counterpart checks. Its Worker is no-store; publication-aware browser storage shares fetch/decode across daily/weekly chunks. This is a code-derived pilot model, not a measured managed-path cost or immutable-cache policy. Managed discovery has a contracted five-minute effective TTL plus immediate Refresh, and immutable products can cache long-term; final managed read/validation chain is not yet an accepted benchmark. [R11]

| Workload | A/C/D/E/F1 after accepted JSON serving | B after a complete safe reverse migration | G/current physical route and key measurement |
| --- | --- | --- | --- |
| 24-hour historical chart | One/two intersecting month products; cold may over-fetch whole month, warm month reuse can dominate. | Same JSON serving; canonical generation does not change it. | Few daily pages; may transfer fewer bytes for a tiny cold request. Measure cold bytes/CPU and warm reuse. |
| Seven-day chart | One/two months, payload shared across chunks. | Same JSON route. | Daily exact discovery/decode; v2 coarse files can transfer/decode unrelated series. |
| Monthly chart | One month if aligned, possibly two for a rolling window. Historical AQI already computed. | Same JSON route. | Many daily reads/chunks/AQI work; budgets remain explicit. |
| 90-day/multi-month chart | Usually three/four calendar months; arbitrary span proportional to intersecting selected products, not daily requests. | Same JSON route. | Many bounded days/pages; dense data may exhaust limits. No unbounded annual endpoint is inferred. |
| Open/current month | Separate accepted recent/canonical/JSON seam and PM context; repeated monthly replacement may over-transfer. | Same seam plus migrated currentness/writers. | Existing canonical-first path covers published history and eligible recent ingest; no already accepted all-JSON replacement. |
| Corrected historical month | Complete affected pair regeneration; next-month PM pair when context changes; retain safe old selection while pending. | Same product amplification, plus v2 writer/receipt adapter. | Canonical/index correction and invalidation; cached results need coherent correction handling. |
| Admin/research/scientific batch | D/C manifest-guided files or approved product; E if frequent exact access is genuinely needed. | Larger groups may help full scans, unmeasured. | Current exact route useful for interactive work; scientific WHO already uses full-file batch. |

Both gzip and Parquet need bounded inflation/decode. Gzip monthly products can increase browser cold bytes/memory, especially for dense networks; avoiding Worker AQI does not prove browser parsing/render cost or network time is acceptable. V3 small segments bound Worker work but still require JSON/identity hashing, ZSTD decode and Station History merge/AQI. E packing reduces stored/PUT/LIST object counts without inherently reducing the two-step index discovery chain. A larger directory or extra catalogue depth can increase cold critical-path latency even when total bytes shrink.

### 9.2 What real TEST acceptance should measure later

Use the existing bounded P2 and separately authorised managed operations, not a speculative pre-implementation test programme. Record cold and warm complete chart latency/settlement, actual Worker CPU and headroom, browser parse/merge/render and memory where observable, compressed/transferred bytes, cache hits and HTTP/R2 GET/HEAD/LIST/PUT counts. Observe generation wall time/CPU/peak memory, source/currentness/evidence bytes, control CAS conflicts, corrected-month/PM-neighbour amplification and writer-commit-to-selected-product lag. Separate recent, open-month, historical and corrected cases.

A matched full-partition baseline decode against retained **equivalent current** v2 data, if available under later authorisation, could distinguish physical-format efficiency; comparing unequal stale populations cannot. Measure all canonical/derived accounts, original evidence, superseded products and failed candidates. No comparative benchmark numbers, synthetic functional suite or automatic cloud operation is supplied here.

For reliability, immutable cached products reduce serving dependence on source decoding/calculation and can remain available during a failed generation attempt. They can also remain stale: do not label an old safe pair current while required changes are unresolved. A small authenticated discovery/control layer becomes a critical dependency. Canonical durable recovery, complete writer evidence and fail-closed selection remain necessary. D/F1 remove redundant mutable representations if correctly implemented; F2 adds a cross-service failure/recovery surface. No managed corruption/missing-product condition triggers automatic canonical Parquet fallback.

## 11. Decisions now, later, and work to avoid

### Decide now

1. **Canonical v3 remains the authority.** No reverse migration, no selector-only rollback, no canonical repacking for index-size concerns.
2. **Continue bounded P2 unchanged.** PR #136/#79 stay isolated source-as-read experiments with their existing readiness/security/admission constraints and separately authorised merge/deployment. This analysis adds no performance result or new blocker to that experiment.
3. **Build managed JSONgen around logical authenticated dependencies, not a permanent exact/`_aligned` format dependency.** Keep today's adapter until replacement is accepted; define the interface so physical encoding can change without rewriting monthly semantics or originals. Complete all-writer coverage/currentness, correction/removal/status and PM-neighbour invalidation first.
4. **Retain monthly per-physical-identity pubIDs and atomic matching observation/AQI pairs.** Preserve immutable originals and fail-closed no-Parquet-fallback behavior. Do not adopt pilot full-sample pubIDs or republish unchanged months without dependency cause.
5. **Resolve a bounded atomic control design before unbounded managed activation.** The current whole-control growth is demonstrably unsuitable as a permanent all-network design. Immutable referenced pages/checkpoints under one CAS authority are preferred for contract review; do not implement independently mutable month authority or simply increase caps.
6. **Make the recent/open-month/Prune-lag seam explicit before default chart cutover.** Keep current accepted routing until the replacement is accepted; no index-retirement project is needed to run P2.

Items 3, 5 and 6 need contract-owner decisions before their dependent managed implementation/activation. They do not require application changes within this documentation task. Current managed selection already fails closed; leave it disabled until its existing integrity gates are met.

### Decide after real TEST acceptance

Accept the full monthly baseline, independent AQI values/context, all applicable verified writer paths, coherent freshness, safe paired publication, discovery/Refresh and actual chart CPU/bytes/latency. Retain G rather than activate managed JSONgen if normal serving meets CPU/headroom needs and observed monthly serving benefits do not outweigh total generation, evidence/control, correction, retention and availability costs. Then decide supported residual API/admin/research access and provenance replacement, manifest-only batch versus compact catalogue versus necessary E-format lookup, event/checkpoint boundaries, retention, and the concrete retirement set. Measure source/evidence/control/version growth alongside products. Physical canonical formats, codecs, pack sizes and service additions depend on an observed problem and can wait.

### Work to avoid

- Reintroducing v2 merely to remove a v3-derived index; combining generations or assuming old v2 includes post-cut-over changes.
- Building a new packed daily chart index before proving a remaining frequent physical consumer.
- Deleting `_aligned` because charts do not fetch it while JSONgen/verifiers still authenticate it, or retaining it forever merely because its current adapter exists.
- Expanding Dropbox backup to include millions of reconstructable lookup objects, or treating derived JSON as canonical recovery.
- Treating a matching digest/count, observed registered events, seven separate inspections, or newer timestamps as complete all-writer currentness.
- Copying full immutable receipt/index bodies into every live control revision; rewriting historical originals to shrink them; independent mutable selectors without a cross-month protocol.
- Adding D1/KV/database dependencies for unmeasured gains; merging observation/AQI formats without changing their accepted contract.
- Premature GC, blanket TTL deletion, new synthetic pre-implementation suites, runtime/Prune/Integrity/schema/configuration/cloud changes or LIVE work in this investigation.

**Genuinely unresolved architecture gates:** the managed publisher lacks complete all-writer/currentness/supersession fencing and an accepted bounded atomic state protocol; default chart cutover additionally lacks an accepted recent/open-month/Prune-publication-gap policy. These block their dependent managed activation/retirement. They do **not** establish a blocker to separately authorised bounded AURN P2. No numerical storage or performance evidence currently justifies returning to v2, rewriting canonical Parquet, or starting an index-rewrite project now.
